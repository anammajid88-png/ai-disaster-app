# AI Disaster App

**Smart, multilingual emergency guidance when every second matters.**

A Pakistan-focused disaster and emergency assistance web application built for the
**Alibaba Cloud AI Hackathon Pakistan 2026**. It combines an AI assistant powered by
Alibaba Cloud Model Studio (Qwen) with verified, offline-capable safety guidance in
**English, Urdu and Hindi**.

## What it does

| Feature | Description |
| --- | --- |
| **AI assistant** | Ask a question by text or voice and get a prioritised, actionable answer in your own language, including Roman Urdu. |
| **Six disaster categories** | Flood, Fire, Earthquake, Storm / Heavy Rain, Road Accident, Medical Emergency — each with a custom animated SVG illustration. |
| **Step-by-step guidelines** | A modal per category: *What to do right now*, then Before / During / After / Avoid, with numbered steps, safety icons and priority levels. |
| **Verified emergency contacts** | Rescue 1122, Police 15, Fire Brigade 16, Edhi 115, Motorway Police 130 — one-tap `tel:` calling, with source and verification metadata. |
| **Emergency kit checklist** | 10 items with a live "6 / 10 Ready" progress display, saved in `localStorage`. |
| **Approximate location** | Optional browser geolocation so you can read your coordinates out to a dispatcher. Nothing is sent to any server. |
| **Voice in and out** | Web Speech API speech-to-text and text-to-speech, with graceful fallbacks. |
| **Works offline** | Guidance, contacts and the kit are available without a network. The AI is clearly marked online-only. |

## Tech stack

**Frontend**

- React 18 + Vite 5
- React Router 6 with `React.lazy` per-route code splitting
- Plain CSS with a design-token system (no UI framework, no CSS-in-JS)
- Custom i18n layer (no i18n dependency)
- Hand-drawn inline SVG for every illustration and icon

**Backend**

- Node.js (>= 18.18) + Express 4
- `helmet`, `cors`, `compression`, `dotenv`
- In-memory per-IP rate limiting
- Native `fetch` + `AbortController` for the Qwen call — no SDK

**AI**

- Alibaba Cloud Model Studio (Qwen) via its OpenAI-compatible endpoint
- Default model `qwen-plus`, configurable

**Storage**

- No database. Safety content lives in versioned JSON under `shared/data/`.
- `localStorage` holds only the kit checklist and the language preference.

Production dependency count is deliberately small: five server packages, two client
packages. Brand images (PNG icons, the Open Graph banner) are generated by a
dependency-free rasteriser in `scripts/`, so there is no image toolchain to install.

## Local setup

**Prerequisites:** Node.js 18.18 or newer (developed on Node 24) and npm.

```bash
# 1. Install both halves of the project
npm run setup

# 2. Create your environment file
cp .env.example .env          # PowerShell: Copy-Item .env.example .env

# 3. Put your Model Studio key in .env
#    ALIBABA_API_KEY=sk-...

# 4. Start the backend and frontend together
npm run dev
```

- Frontend (Vite dev server): <http://localhost:5173>
- Backend (Express API): <http://localhost:5000>

Vite proxies `/api` to the backend in development, so the browser only ever talks to
one origin.

### Running the production build locally

```bash
npm run build     # builds client/dist
npm start         # Express serves the API *and* the built client
```

Then open <http://localhost:5000>.

> The server decides whether to serve `client/dist` when the app is created, so run
> `npm run build` **before** `npm start`. If you build while the server is running,
> restart it.

### The app runs without an API key

If `ALIBABA_API_KEY` is missing or still a placeholder, the app **does not break** and
**does not pretend**. Startup logs a warning, the UI shows an "AI offline — stored
guidance" status, and `/api/chat` answers from the same verified JSON the rest of the
app renders. Every such answer is labelled **"Stored safety guidance"** in the chat.

## Qwen integration

The request path is strictly one-directional:

```
React  ──POST /api/chat──▶  Express  ──HTTPS──▶  Alibaba Model Studio (Qwen)
  ◀────── answer ──────────  Express  ◀────────  Qwen
```

The browser never sees the key, the endpoint or the model name.

**How an answer is produced** (`server/services/aiService.js`):

1. `detectLanguage()` resolves the reply language from the message script and Roman
   Urdu markers, so the user does not have to set anything.
2. `detectDisaster()` scores the message against category keywords and raises urgency
   when it finds life-threatening markers ("not breathing", "بے ہوش", "behosh", …).
3. `promptBuilder.js` builds a system prompt that injects **only** the verified
   contacts from `shared/data/` and the matched category's guidance.
4. `qwenProvider.js` calls the OpenAI-compatible `/chat/completions` endpoint with an
   `AbortController` timeout.
5. On any failure — bad key, timeout, rate limit, malformed response, network error —
   `fallbackService.js` answers from the stored JSON instead.

Every response carries `source: "ai" | "fallback"`, and the UI labels the two
differently. **The app never presents stored guidance as an AI answer.**

**Safety rules in the system prompt:** prioritise immediate safety; answer in the
user's language; never invent an emergency number; use only the contacts supplied by
the app; never claim to have contacted a service, dispatched help or monitored a
location; never fabricate live information such as weather or road status; avoid
dangerous medical instructions; ask at most one clarifying question. For high-risk
situations the required order is: **immediate safety → evacuation or shelter →
electrical, gas and structural hazards → contact emergency services → secondary
advice.**

**Swapping the provider:** implement one module with the same shape as
`qwenProvider.js` and reference it from `aiService.js`. No frontend change is needed.

## API reference

Base path `/api`.

### `POST /api/chat`

```jsonc
// request
{
  "message": "There is water entering my house",
  "language": "en",          // optional; auto-detected when omitted
  "context": "flood",        // optional category hint
  "history": []              // optional prior turns
}
```

```jsonc
// response
{
  "success": true,
  "answer": "…",
  "language": "en",           // language the answer is written in
  "script": "latin",          // latin | arabic | devanagari
  "disasterType": "flood",    // null when no category matched confidently
  "urgency": "high",          // high | normal
  "source": "ai",             // "fallback" when Qwen was unreachable
  "provider": "alibaba-qwen", // null on the fallback path
  "model": "qwen-plus",       // null on the fallback path
  "notice": null              // { code, messageKey, retryable } when guidance
                              // is stored rather than AI-generated
}
```

Errors return `{ success: false, error: { code, messageKey } }`. The client renders
the `messageKey` through its own locale files, so users always see a translated
sentence and never a raw provider error or a stack trace.

| Status | Meaning |
| --- | --- |
| `400` | Missing or empty message, or malformed JSON |
| `413` | Message longer than the allowed length |
| `429` | Rate limit exceeded |
| `503` | AI unavailable *and* no stored guidance matched |

### Content endpoints

| Method | Path | Returns |
| --- | --- | --- |
| `GET` | `/api/health` | Service status and whether AI is configured |
| `GET` | `/api/content/disasters` | All six categories, all languages |
| `GET` | `/api/content/disasters/:id` | One category |
| `GET` | `/api/content/emergency-contacts` | Verified contacts + source metadata |
| `GET` | `/api/content/emergency-kit` | The 10 kit items |

The client bundles the same JSON so every screen works offline; these routes exist so
content can later be updated server-side, or consumed by another client, without a new
frontend build.

## Data architecture

`shared/data/` is the single source of truth, consumed by **both** runtimes:

- the server reads it through `shared/data/index.cjs` (CommonJS)
- the client imports it through the `@shared` Vite alias (ESM JSON)

That is why an offline fallback answer and the guidelines modal can never disagree —
they are rendering the same object.

Each `shared/data/disasters/*.json` file contains an id, accent colours, risk level,
season, primary contact ids, and a `content` block per language with `name`,
`tagline`, `description` and five step arrays: `rightNow`, `before`, `during`,
`after`, `avoid`. Every step has a number, an icon name, a short title, an
explanation and a priority.

`emergencyContacts.json` carries verification metadata — organisation, source URL and
`verifiedOn` date — which the About page displays. **No number in this repository was
invented; there are exactly five, and `npm run validate` enforces that whitelist.**

## Internationalisation

Three languages ship today: **English**, **اردو (Urdu)** and **हिन्दी (Hindi)**.
Selecting one translates the *entire* interface — navigation, headings, buttons,
disaster names and descriptions, all Before/During/After/Avoid steps, warnings,
contact labels, the chat UI, suggested questions, the kit checklist, error messages,
accessibility labels, modals, the footer and the disclaimer.

Urdu renders right-to-left: `<html dir="rtl">`, CSS logical properties throughout,
mirrored icons via an `.icon-flip` helper, and `.num` / `.tel` helpers that keep phone
numbers left-to-right inside RTL text.

**Adding a language** (Punjabi, Sindhi, Pashto and Balochi are the intended next
ones):

1. Add `client/src/i18n/locales/<code>.json` — copy `en.json` and translate.
2. Register the code, native label, direction and speech locale in
   `client/src/i18n/languages.js`.
3. Add a `content.<code>` block to each file in `shared/data/`.
4. Add the code to `LANGUAGES` in `scripts/validate-content.mjs` and run
   `npm run validate` — it will list every key you have not translated yet.

No component code needs to change.

## PWA and offline behaviour

`client/public/service-worker.js` is registered only in production builds.

| Request | Strategy |
| --- | --- |
| Navigations | Network first, falling back to the cached shell |
| `/assets/*` (hashed bundles) | Cache first |
| Icons, manifest, OG image | Stale while revalidate |
| **`/api/*`** | **Never cached, never intercepted** |

That last row is deliberate. The assistant needs a live model, so an offline user gets
a real failure and the app's honest "stored guidance" path — never a stale answer
dressed up as a fresh one. **This app does not claim Qwen works offline.**

Available with no network: the full interface in all three languages, all six
categories and their guidelines, all emergency contacts with working `tel:` links, and
the kit checklist with its saved progress.

Icons and the OG banner are produced by `npm run assets`, which uses a small software
rasteriser and stroke font in `scripts/lib/` — a PNG encoder written on top of
`node:zlib`. No `sharp`, `canvas` or headless browser is required.

## Accessibility

- Interactive controls are sized from a `--touch: 44px` token so that buttons, the
  language switcher and the call links meet the 44 px minimum touch target.
- The guidelines modal is a real dialog: `role="dialog"`, `aria-modal`, focus trap,
  Escape to close, background scroll lock, and focus returned to the trigger.
- Tab strips implement the ARIA tabs pattern with Arrow / Home / End keys.
- Visible focus rings everywhere; icons are `aria-hidden` unless they carry meaning.
- Status changes and chat replies are announced through `aria-live` regions.
- All animation is disabled under `prefers-reduced-motion`.
- The palette is deliberately high-contrast dark-blue-on-white for body text. Contrast
  has not been verified with an automated auditing tool, so treat WCAG AA conformance as
  an intention rather than a measured result.

## Testing

Three runnable harnesses, all checked in.

```bash
npm test                             # static: content, translations, detection
npm run build && npm start           # then, in another shell:
npm run test:smoke                   # live: 54 HTTP checks
```

`npm run validate` checks locale parity in both directions (no missing *and* no
orphan keys), that every `t('…')` key used in the source resolves, that every key
built dynamically from data resolves, that all six categories have complete content in
all three languages with matching step counts, that every icon name in the data is
actually drawn, and that the emergency numbers match the verified whitelist.

`npm run test:detection` runs 35 real phrasings through `detectDisaster()` in English,
Roman Urdu, Urdu script and Hindi script, and asserts both the category and the urgency
level. It also asserts the negative cases, because short stems used to match inside
unrelated words.

`npm run test:smoke` exercises the real server: health, all content endpoints,
multilingual chat with script assertions, disaster detection for all six categories,
urgency escalation, a check that no unlisted phone number appears in an answer,
validation and rate-limit errors, 404s without stack traces, every PWA and SEO file,
SPA deep links, and a scan of the built bundle for leaked credentials.

Current status: **`npm test` passes (no content problems, 35/35 detection cases) and
`npm run test:smoke` is 54 passed, 0 failed.** The app was also walked through manually
in a browser in all three languages — home, guidelines modal, chat, emergency tabs, kit
persistence across reload, About, mobile navigation and the 404 page — with **zero
console errors or warnings**.

Bugs these harnesses caught, all now fixed:

- A life-threatening symptom phrased calmly ("someone collapsed and is not breathing")
  was not escalated to high urgency.
- Four categories referenced a season key no locale defined, printing a raw
  `disaster.season.all-year` key on screen in all three languages.
- Critical-risk categories were mislabelled "Moderate risk" on their cards.
- A blanket icon used by two safety steps silently fell back to a hazard triangle.
- **English continuous phrasing was not detected**: "water is entering my house"
  matched nothing, so a flood question got a clarifying question instead of guidance.
- **Short Urdu and Hindi stems matched inside unrelated words**, because matching was a
  plain substring test. `ہل` ("shake") sits inside `پہلے` ("first"), so *"someone is
  bleeding a lot, what do I do first?"* was routed to **earthquake** guidance. Likewise
  `جل` ("burn") inside `جلدی` ("quickly") and `जल` inside `जलभराव`
  ("waterlogging") both triggered **fire**.
- **The Devanagari nukta spelling `ख़ून` did not match the keyword `खून`** — identical to
  a reader, different codepoints — so a Hindi bleeding question matched no category at
  all. Matching now strips the nukta and Urdu diacritics first.

## Deployment

Not yet deployed — by design. `vercel.json` and `api/index.js` are in place for a
Vercel deployment, which serves `client/dist` statically and runs the Express app as a
serverless function under `/api`.

When you are ready:

1. Push the repository to GitHub. Confirm `.env` is **not** in it.
2. Import the project in Vercel. The build command is `npm run vercel-build`.
3. Add `ALIBABA_API_KEY` (and any overrides) in **Vercel → Settings → Environment
   Variables**. Never put a key in `vercel.json` or any committed file.
4. Leave `CORS_ORIGIN` empty, since the client is served from the same domain.
5. Update the canonical URL in `client/index.html` and the URLs in
   `client/public/sitemap.xml` to your real domain.

## Security notes

- **`ALIBABA_API_KEY` exists only on the server.** It is never prefixed `VITE_`, so
  Vite cannot inline it. It appears in no client file, no HTML, no `localStorage`, and
  no log line.
- `.env` is git-ignored; `.env.example` contains placeholders only.
- The browser calls `/api/chat`; only the server calls Alibaba Cloud.
- Requests are validated and length-capped, and rate-limited per IP.
- Provider errors are mapped to translated message keys — upstream error text and
  stack traces are never returned to the browser.
- `helmet` sets security headers; CORS is restricted to configured origins.
- Geolocation is read in the browser for display only. **Coordinates are never sent to
  the backend or to Alibaba Cloud.**
- `localStorage` holds only the kit checklist and the language choice — no personal
  data, no conversation history.
- The built bundle is scanned for credential patterns as part of `npm run test:smoke`.
